SECTION 2 : PROJECT IDENTIFICATION AND SUMMARY
================================================================================

2.1  PROJECT NAME
     XApp  (displayed in the browser as "XApp — Expense Tracker")

2.2  ONE-LINE SUMMARY
     XApp is a privacy-first, fully client-side personal expense tracker built
     as a Single-Page Application (SPA) with React, TypeScript and Vite. It
     lets a user record, edit, delete, filter and categorize daily expenses,
     set monthly budgets with automatic over-spending warnings, visualise
     spending through three types of charts, export data to CSV, and choose
     between seven display currencies and a light/dark theme — with all data
     persisted in the browser's localStorage and no server of any kind.

2.3  THE PROBLEM BEING SOLVED
     Most people have no accurate, automatic record of where their money goes.
     Bank statements arrive late, spreadsheets are manual and error-prone, and
     existing expense apps frequently demand an account, an internet
     connection and the upload of sensitive financial data to a third-party
     server. There is a clear need for a tool that:
        - records an expense in a few seconds, with minimal friction;
        - classifies spending into meaningful categories automatically at entry;
        - compares actual spending against a limit the user themselves set,
          and warns before the limit is crossed;
        - presents the numbers visually rather than as a wall of text;
        - and does all of this without accounts, without servers, and without
          any data leaving the user's device.

2.4  THE SOLUTION
     XApp is a browser-based application that runs entirely on the client.
     All data lives in the browser's localStorage, giving instant load, full
     offline usability, zero hosting cost, and complete data privacy. It
     provides five screens (Dashboard, Expenses, Budget, Reports, Settings),
     full Create-Read-Update-Delete (CRUD) over expenses, monthly budget
     tracking with an 80% / 100% threshold alert system, three chart types,
     multi-criteria filtering with search and sorting, and CSV export.

2.5  KEY ACHIEVEMENT METRICS (all verified from the code)
     Source files written             : 35 files under src/
     Total lines of code              : approximately 1,859 lines
     React components written         : 27 components + 2 custom hooks
     Screens / routes implemented     : 5
     Reusable UI primitives built     : 7 (Button, Card, Input, Select, Modal,
                                         Badge, ProgressBar)
     Chart components built           : 3 (donut, bar, line)
     Global state slices              : 5 (expenses, budgets, filters, theme,
                                         currency)
     Store actions exposed            : 11
     Expense categories supported     : 8

     Budget alert thresholds          : 80% (warning), 100% (exceeded)

     Runtime dependencies installed   : 11

SECTION 3 : OBJECTIVES OF THE PROJECT
================================================================================

  The project was undertaken with the following objectives. Each objective
  below is stated together with the evidence in the code that shows it was
  actually achieved.

  O1. Provide a fast, frictionless interface for recording an expense,
      requiring no more than four inputs (amount, category, description, date).
      ACHIEVED — ExpenseForm.tsx (138 lines), a controlled form with a
      two-column responsive layout.

  O2. Classify every expense into one of eight fixed, meaningful categories
      so that spending can be analysed by type.
      ACHIEVED — the `Category` string-literal union in types/index.ts with
      8 members, enforced at compile time; a colour is bound to each category
      in the CATEGORY_COLORS map.

  O3. Allow the user to define a monthly spending limit at two levels: one
      overall limit for the month, and an independent limit per category.
      ACHIEVED — the `Budget` type uses `category: Category | 'overall'`, and
      the Budget screen (Budget.tsx, BudgetForm.tsx, BudgetProgress.tsx)
      supports both.

  O4. Warn the user automatically before and after a budget is exceeded,
      rather than letting the overspend be discovered only at month end.
      ACHIEVED — BudgetAlertBanner.tsx implements an 80% warning and a 100%
      exceeded alert, rendered on both the Dashboard and the Budget screen.

  O5. Visualise spending in three complementary ways: composition
      (by category), distribution over time (daily), and long-term trend
      (monthly).
      ACHIEVED — CategoryPieChart.tsx (donut), DailyBarChart.tsx (bar),
      TrendLineChart.tsx (line), all built on Recharts.

  O6. Allow fast retrieval of a specific transaction from a large list using
      text search, category filter and configurable sorting.
      ACHIEVED — utils/filter.ts implements a four-stage pipeline;
      ExpenseFilters.tsx exposes search, category, sort-key and sort-order
      controls; ExpenseList.tsx renders the result.

  O7. Allow the user to take their data out of the application in a portable
      form, so the application cannot become a data trap.
      ACHIEVED — utils/export.ts generates and downloads a CSV of the
      currently filtered result set, with no server involved.

  O8. Respect the user's device: a responsive layout that works on a phone, a
      dark theme for low-light use, and correct currency formatting.
      ACHIEVED — dual navigation (desktop sidebar + mobile bottom tab bar),
      class-based dark mode, and Intl.NumberFormat-based currency formatting
      across 7 currencies.

  O9. Guarantee that no user data leaves the device, and that the application
      works with no internet connection after first load.
      ACHIEVED — there is no fetch, no XHR, no WebSocket, no API call, no
      external runtime dependency on a network resource in the entire
      codebase. All state is in localStorage.

  O10. Maintain a maintainable, strongly-typed, lint-clean codebase.
      ACHIEVED — 100% TypeScript (no JavaScript source files), a strict
      TypeScript configuration, and an ESLint flat config with the recommended
      TypeScript and React Hooks rule sets.

SECTION 4 : SCOPE OF THE PROJECT
================================================================================

4.1  IN SCOPE (implemented and working)
     - Creating, viewing, editing and deleting expense records
     - Eight fixed expense categories
     - Marking an expense as recurring, with weekly / monthly / yearly interval
     - Setting, updating and removing monthly budgets (overall + per category)
     - Budget utilisation progress bars with colour-coded thresholds
     - Automatic budget warning and exceeded alerts
     - Dashboard with four Key Performance Indicators (KPIs)
     - Month-over-month spending comparison
     - Three chart visualisations
     - Text search, category filtering, and sorting by date / amount / category
       in both ascending and descending order
     - CSV export of the filtered result set
     - Light / dark theme switching with no flash-of-wrong-theme on load
     - Choice of 7 display currencies
     - Destructive "clear all data" with a confirmation prompt
     - Responsive layout for mobile, tablet and desktop

4.2  OUT OF SCOPE (deliberately not implemented — see Section 20 for reasons)
     - Any server-side component, API or database
     - User accounts, authentication, sign-in, or multi-user support
     - Cloud synchronisation or cross-device data sharing
     - Income tracking, transfers between accounts, or bank reconciliation
     - Real foreign-exchange conversion (amounts are re-labelled, not converted)
     - Automated recurring-expense generation (recurrence is recorded but not
       materialised as future transactions)
     - Receipt or invoice image upload
     - Notification / reminder system
     - Service Worker, offline caching, or installable PWA behaviour
     - Analytics, telemetry or error reporting
     - Internationalisation / localisation (the UI is English-only)
     - Automated test suites

4.3  TARGET USER
     A single individual who wants a private, low-friction record of personal
     spending. The design assumes one user, one device, one browser profile.

4.4  SCOPE JUSTIFICATION (for the report's Scope chapter)
     The project deliberately stops at the client. This is a scope decision,
     not an oversight: a serverless design makes the application free to host,
     instantly responsive, trivially private, and demonstrable without
     provisioning infrastructure — which is appropriate for a minor project
     whose primary aim is to demonstrate mastery of modern front-end
     engineering, state management, and data visualisation.

  NFR-01  Performance. The application shall render without perceptible delay
          on a mid-range device. Basis: 27 components with no lazy loading;
          the heaviest computed operation is a filter+sort over the expense
          array, which is O(n log n) and trivial at personal-data volumes
          (hundreds to low thousands of records).

  NFR-02  Responsiveness. The layout shall adapt from a 320 px mobile viewport
          to a wide desktop viewport. Basis: Tailwind mobile-first responsive
          prefixes throughout (sm:, md:, lg:), a slide-in drawer plus a fixed

          interactions. Basis: "Add Expense" is a single button on the
          Expenses screen; deleting is a single icon button per row.

  NFR-04  Data privacy. No user data shall be transmitted off the device.
          Basis: zero network calls in the entire source tree; all
          persistence is localStorage.

  NFR-05  Offline operation. After the page is loaded, all functionality shall

7.3  WHY EACH TECHNOLOGY WAS CHOSEN  (use this for the report's
     "Technology Stack" and "Tool Selection" chapter)

  React 19 — chosen for its component model, one-way data flow, and the
  declarative approach that lets the UI be described as a function of state.
  The StrictMode wrapper in main.tsx additionally surfaces impure renders
  and side-effect bugs during development. React 19 also makes
  `use`-style and the modern client API (`react-dom/client`) the default.

  TypeScript 6 — the project's data model is the foundation of every feature
  (budget matching, category colours, chart grouping). A string-literal union
  for categories means an invalid category is a compile error rather than a
  runtime bug. `tsc -b` runs before every production build, so a type error
  breaks the build. Three compiler options are worth highlighting in the
  report: `verbatimModuleSyntax` (forces `import type` for type-only imports,
  keeping the emitted bundle smaller), `erasableSyntaxOnly` (forbids TypeScript
  `enum` and `namespace` in favour of erasable syntax, which is what motivated
  the union-type approach), and `noUnusedLocals` / `noUnusedParameters`.

  Vite 8 — chosen for its native-ESM dev server and near-instant Hot Module
  Replacement (HMR), which materially shortens the feedback loop during
  development. It also produces a hashed, minified production bundle. The
  build command is deliberately `tsc -b && vite build` so that type checking
  is a gate on production builds rather than a separate manual step.

  Zustand 5 — the central architectural decision. Zustand was chosen over
  Redux because it provides the same single-store, unidirectional-data-flow
  model with a fraction of the boilerplate: no action-type constants, no action
  creators, no reducers, and no provider wrapping the tree. Its
  `persist` middleware provides localStorage persistence out of the box, and
  its atomic selector subscriptions (`useStore(s => s.theme)`) let a
  component re-render only when the slice it actually uses changes — which
  matters in a 27-component tree. See Section 10.4 for the trade-off that was
  accepted in exchange.

  React Router DOM 7 — provides declarative, nested client-side routing with a
  `NavLink` component that knows whether it is active, plus an `Outlet` slot
  that enables the layout-route pattern (Section 11.3). No page reload occurs
  during navigation.

  Recharts 3 — a React-idiomatic wrapper over SVG chart primitives. It was
  chosen over Chart.js (which requires imperative canvas manipulation and a
  separate wrapper library) and over D3 (a much larger surface area with a
  steeper learning curve, disproportionate for three charts). Recharts is
  declarative, works with function components, and provides
  `ResponsiveContainer` for free, which is essential for the responsive
  requirement NFR-02.

  Tailwind CSS 4 — chosen for utility-first styling: rapid iteration without
  leaving the markup, consistent spacing and colour scales, and responsive
  variants (`sm:`, `md:`, `lg:`) as first-class primitives. Version 4 is
  configured CSS-first via the `@theme` and `@custom-variant` at-rules inside
  src/index.css, with no JavaScript config file and no PostCSS config,
  because the Vite plugin handles the pipeline.

  date-fns — a modular, tree-shakeable alternative to Moment.js. Only the
  specific functions needed are imported (`parseISO`, `isWithinInterval`,
  `format`), so the bundle stays small. `isWithinInterval` gives inclusive
  date-range comparison without hand-written millisecond arithmetic.

  lucide-react — provides a consistent, single-weight, tree-shakeable SVG icon
  set, used instead of an icon font (which requires extra network requests and
  carries accessibility and FOUT problems) or hand-written SVGs.

  uuid — RFC-4122 version 4 identifiers. Chosen over `crypto.randomUUID()`
   only for consistency of the call style; and over auto-increment integers
  because array indices are not stable identifiers once records are deleted
  or sorted, whereas a UUID survives both.

  Intl.NumberFormat (built into the browser, no library) — used instead of a
  date/number library for currency. It produces correctly localised output for
  every supported currency symbol and thousands separator with no custom
  formatting code.

7.4  COMPARATIVE STUDY OF EXISTING SOLUTIONS
     (for the report's "Literature Survey" / "Existing System" chapter.
      Add real citations — see Section 22. Do NOT add statistics or market
      figures unless you have a citable source.)

  Solution class A — Manual methods (notebook, spreadsheet, bank passbook).
     Strengths: zero cost, no learning curve, universally available.
     Weaknesses: high chance of manual error; no automatic categorisation;
     no real-time totals; no alerts; no visual analysis; analysis of a
     multi-month history by hand is impractical.
     How XApp differs: removes the manual aggregation step by computing
     totals, averages, comparisons and charts automatically.

  Solution class B — Bank-provided transaction and spend analysers.
     Strengths: accurate, because they read real settlement data; often free
     with a bank account.
     Weaknesses: they are read-only — a user cannot add a cash purchase made
     outside the account; category schemes are bank-specific and fixed; data
     access depends on the bank's own aggregation, which is outside the user's
     control; and a user without a qualifying account has nothing.
     How XApp differs: the user is the source of truth and can edit or delete
     any record, and can define personal categories and budgets.

  Solution class C — Proprietary commercial expense and budgeting applications.
     Strengths: mature, polished, often include bank synchronisation,
     multi-device sync, receipt capture and shared/team budgets.
     Weaknesses: typically require account creation and transmit sensitive
     financial data to a third-party server; many free tiers gate data export
     or multi-currency behind a paid subscription; behaviour may change
     remotely with no user control.
     How XApp differs: requires no account, sends no data anywhere, is fully
     functional at no cost, and the data format (plain JSON in localStorage,
     exportable as CSV) is entirely under the user's control.

  Solution class D — Open-source / self-hosted personal finance tools.
     Strengths: open, auditable, no vendor lock-in.
     Weaknesses: typically require technical deployment skills (server,
     database, command line) and are not aimed at a non-technical single user.
     How XApp differs: `npm install && npm run dev` is the entire setup; there
     is no server, container or database to provision.

  Contribution of this project
     XApp deliberately occupies the gap between "too manual" and "requires an
     account and a server": a single-user, zero-configuration, offline-capable
     tool that provides the automation and visualisation of a modern expense
     application while keeping every byte of data on the user's own device.
     Its acknowledged trade-off is that, having no backend, it cannot sync
     across devices — this is stated as a limitation in Section 20, not hidden.

7.5  ALTERNATIVES CONSIDERED AND REJECTED
     (use for a "Choice of Technology" justification subsection)

     Redux + React-Redux  -> Rejected. Requires action-type string constants,
        action creators, reducers and a <Provider> wrapper. For five state
        slices and eleven simple functions this is a large amount of
        boilerplate with no benefit. Zustand provides the same unidirectional
        data flow with a fraction of the code and no provider.

     Context API (useContext) alone  -> Rejected. A single large context value
        re-renders every consumer whenever any part of it changes. Zustand's
        atomic selector subscriptions avoid this and remove the need for the
        common Provider/useMemo/useRef boilerplate.

     Material UI / Ant Design  -> Rejected. A large component library imposes
        its own visual language and a significant bundle cost. The project
        needs only 7 primitives, which were hand-written in a total of
        208 lines, giving complete control over the light/dark theme and
        zero extra dependency weight.

     Firebase / Supabase / any backend  -> Rejected for this project. It adds
        authentication, network latency, a hosting account, a data-privacy
        surface and a failure mode, none of which is needed to demonstrate the
        project's objectives. Documented as Future Work item F-02 instead.

     Chart.js  -> Rejected. Imperative canvas API; needs a React wrapper and
        manual lifecycle management, which conflicts with React's declarative
        model and complicates responsive resizing.

     D3.js  -> Rejected. Far larger scope than three charts requires, and a
        steeper learning curve disproportionate to the project's aim.

     Moment.js  -> Rejected in favour of date-fns: Moment is not tree-shakeable
        and is effectively in maintenance mode; date-fns v4 is modular and
        ESM-first.

     IndexedDB  -> Deferred. localStorage was sufficient for the data volume
        of a personal expense record (well under the ~5 MB origin quota) and is
        synchronous, which keeps the state logic simple. Recorded as Future
        Work item F-04 for when photo receipts are added.

8.1  ARCHITECTURAL STYLE: LAYERED, CLIENT-ONLY SINGLE-PAGE APPLICATION
     The system is a three-tier browser application in which the entire server
     tier is eliminated and the "data tier" is replaced by the browser's
     localStorage. Nothing crosses the network.

                        ┌──────────────────────────────────────────┐
                        │              BROWSER / CLIENT            │
                        │                                          │
   ┌────────────────────┴──────────────────────────────────────────┴───────────┐
   │  PRESENTATION LAYER  (src/pages, src/components)                       │
   │  27 React components.  Renders state.  Dispatches intent to the store.  │
   │  Owns ONLY ephemeral UI state (modal open?, which row is being edited). │
   └───────────────────────────────┬──────────────────────────────────────────┘
                                   │  useStore(selector)  /  useStore.action()
   ┌───────────────────────────────┴──────────────────────────────────────────┐

   │  Single Zustand store.  5 state slices, 11 actions, all mutations here. │
   │  Owns the data model and every write to application state.              │
   └───────────────────────────────┬──────────────────────────────────────────┘
                                   │  JSON.stringify / JSON.parse
   ┌───────────────────────────────┴──────────────────────────────────────────┐
   │  UTILITY LAYER  (src/utils, src/hooks)                                  │

   └───────────────────────────────┬──────────────────────────────────────────┘

     Cross-cutting concerns:
       - index.html inline script  -> applies the dark class before first paint
       - src/index.css             -> Tailwind v4 theme + class-based dark mode

     Consequences of this style, for the report's "Advantages" subsection:
       - Zero server cost and zero infrastructure to deploy.
       - Instant response: every mutation is a synchronous local state update,
         so there is no loading spinner anywhere in the application.
       - Works fully offline; there is no network failure mode to handle.
       - Privacy by construction: the data never leaves the browser.
       - Single-user by construction: there is no concept of two users, and
         no data can be shared between browsers.

8.2  REQUEST / RESPONSE LIFECYCLE  (use as Figure 2's caption narrative)
     1. The user opens the URL. The browser fetches index.html, one hashed
        JavaScript bundle and one hashed CSS file. The inline head script
        reads localStorage and applies the dark class BEFORE first paint, so
        there is no white flash.
     2. React mounts at #root. App.tsx installs BrowserRouter, which matches
        the current URL against the route table and renders AppLayout with
        the matching page inside its <Outlet>.
     3. AppLayout's useEffect subscribes to the theme slice and keeps the
        <html> class in sync.
     4. The page component subscribes to the slices it needs. A selector
        returning a primitive (or a stable function reference) means only the
        components that read a changed slice re-render.
     5. The user acts. The handler calls a store action. The action computes
        the next state with the functional form of `set`, which guarantees it
        always sees the latest state.
     6. The persist middleware serialises the new state to localStorage.
     7. Subscribed components re-render; derived data (totals, charts, budget
        percentages) is recomputed with pure functions from src/utils.
     There is no step in this lifecycle that touches the network after the
     initial asset load.

8.4  DESIGN PATTERNS AND TECHNIQUES USED
     (This is the strongest section for the report's "Design Methodology"
      chapter. Each pattern is listed with its evidence.)

  P-01  Single Source of Truth / centralised state
        All application data lives in one store; components hold no copies.
        Evidence: useStore.ts is the only place expenses or budgets are
        written.

  P-02  Unidirectional data flow
        UI event -> store action -> new state -> re-render. There is no path by
        which a component mutates data directly.
        Evidence: every handler in the codebase calls a store action.

  P-03  Immutable state updates via the functional `set` form
        Evidence: useStore.ts uses `set((state) => ...)` in all 11 actions;
        utils/filter.ts starts with `let filtered = [...expenses]` specifically
        so that the subsequent `.sort()` cannot mutate the store's array.

  P-04  Atomic (selector) state subscription
        A component subscribes to the narrowest slice possible, so unrelated
        state changes do not cause a re-render.
        Evidence: `useStore((s) => s.theme)`, `useStore((s) => s.addExpense)`.

  P-05  Container / Presentational separation
        Page components are thin orchestrators that own modal visibility and
        delegate everything else.
        Evidence: pages/Expenses.tsx (58 lines) owns only `showForm` and
        delegates the list to ExpenseList and the controls to ExpenseFilters.

  P-06  Variant / compound-prop design system
        One primitive, many looks, selected by a typed prop.
        Evidence: Button.tsx declares `variant?: 'primary' | 'secondary' |
        'danger' | 'ghost'` and `size?: 'sm' | 'md' | 'lg'` over lookup maps,
        giving 12 combinations from 37 lines.

  P-07  Native-attribute interface extension
        Primitives extend the DOM's own TypeScript interfaces and spread
        `{...props}`, so the entire native API is available and fully typed
        without being reimplemented.
        Evidence: `ButtonProps extends ButtonHTMLAttributes<HTMLButtonElement>`,
        `InputProps extends InputHTMLAttributes<HTMLInputElement>`,
        `SelectProps extends SelectHTMLAttributes<HTMLSelectElement>`,
        `CardProps extends HTMLAttributes<HTMLDivElement>`.

  P-08  Single component, two modes (polymorphic behaviour by prop)
        Evidence: ExpenseForm's optional `editExpense` prop. State is seeded
        with `editExpense?.x || default`, submission branches
        `if (editExpense) updateExpense(...) else addExpense(...)`, and the
        submit label becomes "Update Expense". Roughly 30 lines saved versus a
        separate EditForm.

  P-09  Guard-clause / early-return control flow
        Business rules are expressed as sequential early returns rather than
        nested conditionals.
        Evidence: BudgetAlertBanner.tsx: `if (!overallBudget) return null;`
        then `if (pct < 80) return null;`. Modal.tsx: `if (!open) return null;`
        which also unmounts the dialog rather than hiding it.

  P-10  Single-pass grouping (O(n)) instead of repeated filtering (O(k*n))
        Evidence: Dashboard.tsx builds `totalsByCategory` in one `for...of`
        loop, and both DailyBarChart and TrendLineChart accumulate into a
        `Record<string, number>` in one pass. This replaced an earlier
        O(k*n) nested-filter version during refactoring (see Section 18.2).

  P-11  Registry-driven configuration
        One declarative source enumerates categories, their labels and their
        colours; every component that needs to iterate, display or colour a
        category reads from it.
        Evidence: `CATEGORIES`, `CATEGORY_LABELS: Record<Category, string>`,
        `CATEGORY_COLORS: Record<Category, string>`. Because the maps are typed
        `Record<Category, ...>`, omitting a category is a COMPILE error.

  P-12  Null-safe access and division guards
        Evidence: `avgDaily` is computed only when `monthExpenses.length > 0`;
        `monthChange` is guarded on `totalLastMonth > 0`;
        ProgressBar computes `max > 0 ? Math.min((value/max)*100, 100) : 0`.

  P-13  Derived-state, not stored-state
        Totals, averages, top category and chart series are computed during
        render from the raw records. Nothing derived is written to the store,
        so it can never go stale.
        Evidence: Dashboard.tsx and all three chart components.

  P-14  Config-array-driven form controls
        The Select primitive takes `options: { value, label }[]` decoupled from
        the domain types, which lets it serve the currency list, the category
        list, the interval list and the sort controls with one component.
        Evidence: Select.tsx maps `options` to `<option>`.

  P-15  Class-based dark mode with a pre-paint guard
        Evidence: `@custom-variant dark (&:where(.dark, .dark *))` in index.css
        plus the inline script in index.html. The store is the source of truth;
        the DOM class is kept in sync by a single useEffect in AppLayout.

  P-16  Pre-emptive DOM pitfall avoidance
        Evidence: `prevMonthKey()` in utils/date.ts sets the day to 1 BEFORE
        decrementing the month, so that a date such as 31 March cannot overflow
        into an unexpected month.

  P-17  Type-level exhaustiveness as a correctness tool
        The absence of TypeScript `enum` (mandated by `erasableSyntaxOnly`) was
        turned into an advantage: a string-literal union with `Record<Category,
        string>` companion maps makes an unhandled category a build failure.

9.1  WHY THE MODEL LOOKS THIS WAY  (important for the "Data Design" chapter)
     The project has no SQL database, so the "data design" is a document /
     JSON object design. Say this explicitly in the report rather than
     pretending there is a schema. Four decisions are worth explaining:

     (a) Dates are stored as STRINGS, not as Date objects or epoch numbers.
         `Expense.date` is a 'YYYY-MM-DD' string and `createdAt` is a full
         ISO-8601 timestamp. Reasons: it round-trips losslessly through the
         native <input type="date"> element, it survives JSON
         serialisation to localStorage without a conversion step or a
         timezone shift, and ISO-8601 strings sort lexicographically, so
         `a.date.localeCompare(b.date)` is a correct chronological sort.

     (b) Category is a string-literal UNION, not a TypeScript enum. The
         compiler setting `erasableSyntaxOnly: true` forbids enums, and the
         union is better anyway: it is erasable (so bundlers need no helper),
         it is checked exhaustively, and it composes with `Record<Category,
         string>` to give compile-time completeness guarantees.

     (c) Budget has NO id. Its natural key is the composite
         (category, month). This is not an oversight — it is what makes the
         store's upsert possible (Section 10.3) and it prevents duplicate
         budgets for the same category in the same month by construction
         rather than by a validation rule. It also demonstrates an
         understanding of natural versus surrogate primary keys, which is
         good report material.

     (d) Filters live INSIDE the persisted store, not in component state.
         Consequence: the user's last search text and sort order survive a
         page reload. This is a deliberate UX decision. Its side effect is
         noted as Limitation L-07.

     Notable design points to write about:
     - `addExpense` takes `Omit<Expense, 'id' | 'createdAt'>`. The TYPE SYSTEM
       prevents a caller from supplying an id or a timestamp. Identity and
       auditing are the store's responsibility, not the caller's.
     - `addExpense` PREPENDS (`[newExpense, ...state.expenses]`), so the newest
       record is always at the top of the array.
     - `updateExpense` is a partial merge (`{ ...e, ...data }`), so omitted
       fields are preserved — a true partial update, not a replace.
     - `setFilters` shallow-merges, which is exactly what allows three
       independent filter controls to share one action.
     - `clearAll` deliberately preserves `theme` and `currency` — it is a data
       wipe, not a state reset. Losing a user's dark-mode and currency choice
       on a data deletion would be poor behaviour.
     - All 11 actions use the FUNCTIONAL form of `set`, `set((state) => ...)`.
       This is not stylistic: the functional form always receives the latest
       state, which makes the actions safe under rapid successive calls (e.g.
       the user typing quickly into the search field, which calls
       `setFilters` on every keystroke).

10.3  THE BUDGET UPSERT  (worth a full sub-section in the report)
     Because `Budget` has no id, `setBudget` locates a record by its natural
     key:

         const idx = state.budgets.findIndex(
           (b) => b.category === budget.category && b.month === budget.month
         );
         const newBudget: Budget = { category, amount, month };   // narrowed
         if (idx >= 0) {
           const updated = [...state.budgets];
           updated[idx] = newBudget;
           return { budgets: updated };
         }
         return { budgets: [...state.budgets, newBudget] };

     Points to make:
       - It is an UPSERT expressed in eight lines, with no reducer boilerplate.
       - It copies the array before index assignment, so the previous state is
         never mutated (essential for correct change detection).
       - It explicitly re-lists the three `Budget` fields, which strips any
         stray property — a deliberate narrowing for data hygiene.
       - The user experience consequence is that re-submitting a budget for
         the same category and month silently overwrites it. No "updated"
         confirmation is shown. See Limitation L-08.

10.4  PERSISTENCE MIDDLEWARE
     `persist(..., { name: 'expense-tracker-store' })`
     - Default storage is localStorage; default serialisation is JSON.
     - There is NO `partialize`, so all five slices are written, including
       `filters` (Limitation L-07).
     - There is NO `version` / `migrate` option, so the stored payload is
       unversioned. Changing the data model later would require a migration
       strategy (Future Work item F-06).
     - There is NO `onRehydrateStorage` callback.
     - Because persistence is synchronous, the store is already populated
       before the first render — there is no loading state to design, and no
       "flash of empty UI" problem. This is a genuine advantage of localStorage
       over IndexedDB or a network fetch, and it is worth stating in the
       report.

10.5  SUBSCRIPTION STYLES USED  (an honest architectural observation)
     Two styles coexist:
       (i)  Atomic selectors — `useStore((s) => s.theme)`,
            `useStore((s) => s.addExpense)`, `useStore((s) => s.setBudget)`.
            Used in AppLayout, Header, useFormatCurrency, ExpenseForm,
            BudgetForm. These re-render only when that exact value changes.
       (ii) Whole-store destructuring — `const { expenses, filters } =
            useStore()`. Used in Expenses, ExpenseList, ExpenseFilters,
            Dashboard, Reports, Settings, BudgetProgress, BudgetAlertBanner.
            This subscribes the component to the entire store, so ANY slice
            change re-renders it.
     Style (ii) is functionally correct but suboptimal. Its visible symptom is
     that the filter pipeline is executed twice per render cycle on the
     Expenses screen, because both Expenses.tsx and ExpenseList.tsx call
     `filterExpenses(expenses, filters)` independently and neither is
     memoised. Recorded as Limitation L-05 with the fix in Section 21.
     Present this as a recognised trade-off discovered during review — it is a
     better report than claiming a flaw-free design.

SECTION 13 : ALGORITHMS AND CORE BUSINESS LOGIC

  These are the code sections an examiner will actually look for. Give each

13.1  ALGORITHM 1 — THE FILTER AND SORT PIPELINE
       File: src/utils/filter.ts   Complexity: O(n log n) worst case.

       filterExpenses(expenses, filters) executes four stages in a fixed
       order, each conditional on its own filter being active:

         Stage 0  COPY
                 let filtered = [...expenses];
                 WHY: the final stage calls .sort(), which mutates in place.
                 Copying guarantees the store's array is never mutated and
                 referential equality checks remain valid.

         Stage 1  DATE RANGE  (only if filters.dateRange !== null)
                 parse both endpoints, then keep entries whose date falls
                 within the interval, using date-fns' isWithinInterval
                 (inclusive of both endpoints).

         Stage 2  CATEGORY  (only if filters.categories.length > 0)
                 keep entries where categories.includes(e.category).
                 Modelling a single selection as a ONE-ELEMENT ARRAY is what
                 makes multi-category selection possible later without any
                 change to the filter logic or the stored shape.

         Stage 3  SEARCH  (only if filters.search is non-empty)
                 lowercase the query once, then keep an entry if its
                 description OR its category key contains the query.
                 Searching the raw category key as well as the description
                 means typing "food" matches, even though the user only ever
                 sees the label "Food & Dining". This is a deliberate
                 usability decision worth describing in the report.

         Stage 4  SORT  (always)
                 compute a three-way comparison:
                   sortBy 'date'     -> a.date.localeCompare(b.date)
                                          (correct because ISO-8601 dates sort
                                           lexicographically)
                   sortBy 'amount'   -> a.amount - b.amount   (numeric)
                   sortBy 'category' -> a.category.localeCompare(b.category)
                 then negate for descending:
                   return sortOrder === 'asc' ? cmp : -cmp;

       Also exported from this file:
         getMonthKey(dateStr) => dateStr.slice(0, 7)
       which converts 'YYYY-MM-DD' to 'YYYY-MM' by taking the first seven
       characters. This is the month-bucketing primitive used by the
       Dashboard and both budget components.

       Observations to include in the report:
         - Each stage is independent and skipped entirely when its filter is
           inactive, so the common "no filters" case costs one O(n log n) sort
           and nothing else.
         - The function is PURE: same inputs give the same output, and it
           mutates nothing. It is therefore straightforward to unit test —
           see Future Work item F-01.
         - It is currently called twice per render on the Expenses screen
           (Limitation L-05).

13.2  ALGORITHM 2 — EXPENSE CREATE / EDIT (single form, two modes)
       File: src/components/expenses/ExpenseForm.tsx

       Mode is inferred from a single optional prop, `editExpense`:

         1. SEED STATE from the prop, with a default for each field:
              amount      = editExpense?.amount.toString() || ''
              category    = editExpense?.category   || 'food'
              description = editExpense?.description|| ''
              date        = editExpense?.date       || todayISO()
              isRecurring = editExpense?.isRecurring|| false
              recurringInterval = editExpense?.recurringInterval || undefined
            All inputs are CONTROLLED: the value comes from state and every
            keystroke calls setForm({ ...form, field: value }) — a hand-rolled
            form reducer using the object-spread idiom.

         2. VALIDATE on submit, collecting errors into a
            Record<string, string> MAP (field name -> message), so a single
            Input can display `${errors.amount}`:
              amount      : must be present, not NaN, and > 0
              description : must be non-empty AFTER trim()  (rejects "   ")
              date        : must be present
            If any error exists, the submit returns early and nothing is
            dispatched.

         3. NORMALISE the payload:
              amount      = Number(form.amount)
              description = form.description.trim()
              recurringInterval = form.isRecurring ? form.recurringInterval
                                                   : undefined
            The last line is a genuine data-hygiene rule: an interval is never
            stored on a non-recurring expense, so no orphaned data can exist.

         4. DISPATCH:
              if (editExpense) updateExpense(editExpense.id, data);
              else               addExpense(data);
            (addExpense is type-restricted to Omit<Expense,'id'|'createdAt'>,
             so data has no id — the store supplies one.)

         5. CLOSE by calling the onClose() prop.

         Conditional UI: checking "Recurring" reveals an additional Select
         ("Repeat every": Weekly / Monthly / Yearly). The select's displayed
         value falls back to 'monthly' when nothing is stored yet.

13.3  ALGORITHM 3 — MONTH BUCKETS AND THE PREVIOUS MONTH
       File: src/utils/date.ts

       pad(n)                  -> n.toString().padStart(2, '0')
       todayISO()              -> YYYY-MM-DD from the LOCAL date
       currentMonthKey()       -> YYYY-MM
       monthKeyOf(date)        -> YYYY-MM
       prevMonthKey()          -> previous YYYY-MM

       Two implementation details here are excellent report material:

       (a) LOCAL time, not UTC. The helpers use getFullYear / getMonth /
           getDate, NOT toISOString(). This is deliberate: toISOString()
           converts to UTC, so for a user in a timezone ahead of UTC a
           transaction entered late in the evening would be filed under
           tomorrow's date. Local-time arithmetic keeps "today" meaning what
           the user thinks it means.

       (b) The month-overflow pitfall is handled correctly. Decrementing a
           JavaScript month in place can overflow when the day-of-month does
           not exist in the target month — 31 March minus one month can land
           on 3 March instead of February. The code therefore sets the day to
           1 FIRST, and only then decrements the month:
             d.setDate(1);
             d.setMonth(d.getMonth() - 1);
       This is a real, commonly-missed edge case and mentioning it shows
       genuine understanding of the Date API.

13.4  ALGORITHM 4 — DASHBOARD KPIs
       File: src/pages/Dashboard.tsx

       (a) MONTH SPLIT — two filters over the same array, using getMonthKey
           to compare a 'YYYY-MM' key against the current and previous month.

       (b) MONTHLY TOTAL — a reduce summing amounts.

       (c) DAILY AVERAGE = totalMonth / new Date().getDate(),
           guarded by `monthExpenses.length > 0`. Be precise in the report:
           this divides by the number of ELAPSED days in the month, so it is
           an "average so far" figure that will fall as the month progresses
           and stabilise at the true mean. It is NOT a division by 30 or 31.

       (d) PER-CATEGORY TOTALS in a SINGLE pass:
             const totalsByCategory: Partial<Record<Category, number>> = {};
             for (const e of monthExpenses) {
               totalsByCategory[e.category] =
                 (totalsByCategory[e.category] ?? 0) + e.amount;
             }
           Note the `Partial<Record<...>>` type and the `?? 0` default. The
           empty record is the accumulator; this is O(n).

       (e) TOP CATEGORY as a running maximum over the fixed CATEGORIES array
           (not over the expenses), seeded with
           `{ category: null, amount: 0 }` so that the "no data" case is
           representable and displays as "N/A". Iterating CATEGORIES rather
           than the expense list guarantees the answer is always a valid
           category, and makes the result independent of record order.
           This replaced an earlier nested filter+reduce per expense
           (Section 18.2).

       (f) MONTH-OVER-MONTH CHANGE:
             ((totalMonth - totalLastMonth) / totalLastMonth) * 100
           with a guard for a zero denominator, falling back to 0.
           IMPORTANT INTERPRETATION POINT for the report: the value is
           displayed with `positive: monthChange <= 0` and a "vs last month"
           caption. Because spending going DOWN is a good outcome, the sign
           convention is inverted relative to a generic trend indicator. This
           is correct behaviour but is easy to misread, so explain it rather
           than leaving it for the examiner to puzzle over.

       (g) RECENT 5 — copy, sort DESCENDING by date, slice(0, 5). A simple
           top-N; note that it is not memoised.

13.5  ALGORITHM 5 — BUDGET UTILISATION AND THE ALERT THRESHOLDS
       Files: BudgetAlertBanner.tsx, BudgetProgress.tsx, ProgressBar.tsx

       (a) SPENT THIS MONTH = expenses filtered to the current month key,
           then reduced to a sum. This exact three-line derivation is
           duplicated in three components (Dashboard, BudgetAlertBanner,
           BudgetProgress) — a clear DRY violation, recorded as
           Limitation L-14.

       (b) OVERALL BUDGET = budgets.find(b =>
               b.category === 'overall' && b.month === currentMonth)

       (c) UTILISATION = (totalSpent / budget.amount) * 100

       (d) THE DECISION LOGIC, expressed as guard clauses:
             if (!overallBudget) return null;      // nothing set -> no banner
             if (pct < 80)           return null;  // under 80%   -> no banner
             const isOver = pct >= 100;
           So the banner renders only when a budget exists AND utilisation is
           at least 80%. Two visual states follow:
             >= 100% : red border / red-50 background / red-800 text
                       message: "Budget exceeded! You've spent X of Y"
             >=  80% : yellow border / yellow-50 background / yellow-800 text
                       message: "Budget warning: You've spent N% (X of Y)"
           Both states have full dark-mode counterparts.

       (e) PROGRESS BAR (ui/ProgressBar.tsx) — three pieces of logic:
             GUARDED DIVISION:  max > 0 ? Math.min((value / max) * 100, 100) : 0
               The `max > 0` test prevents NaN or Infinity from a zero budget,
               and Math.min CLAMPS the fill at 100% so an overspend cannot
               overflow its track.
             THREE-TIER COLOUR: >= 100% -> bg-red-500
                                >=  80% -> bg-yellow-500
                                else    -> bg-green-500
               These are complete static class-name strings chosen at runtime,
               so Tailwind's scanner finds them in the source and they are
               genuinely present in the built CSS. Contrast this with Badge,
               which needs inline styles because its colours are computed.
             ANIMATION: `transition-all duration-300` on the fill, so the bar
               grows smoothly when a new expense is added.

       (f) PER-CATEGORY SPEND is a second filter+reduce inside the map over
           category budgets, giving O(k*n) for k category budgets. A
           single-pass groupBy would make it O(n) — see Future Work F-03.

       INCONSISTENCY WORTH ADMITTING: ProgressBar guards against a zero
       maximum, but BudgetAlertBanner divides without a guard. It is safe
       today only because BudgetForm rejects amounts <= 0. Two components
       applying the same formula should apply the same guard.

13.6  ALGORITHM 6 — CHART DATA AGGREGATION
       Three charts, three bucket granularities, two different strategies.

       (A) CategoryPieChart — DONUT, 8-PASS GROUPING
             data = CATEGORIES
               .map(cat => ({
                 name:  CATEGORY_LABELS[cat],
                 value: expenses.filter(e => e.category === cat)
                                  .reduce((sum, e) => sum + e.amount, 0),
                 color: CATEGORY_COLORS[cat],
               }))
               .filter(d => d.value > 0);
           The trailing filter is essential: it removes zero-value categories
           so the donut has no invisible slices and the legend is not padded
           with eight entries of which several are zero.
           Rendered as a donut: innerRadius 60, outerRadius 100,
           paddingAngle 3 for slice separation, with one <Cell> per data
           point carrying its own colour.
           COST: 8 x n, i.e. O(k*n) — the array is re-scanned once per
           category. This is the one aggregation in the project that has NOT
           been converted to a single pass. Honest point for the report;
           fix given as Future Work F-03.

       (B) DailyBarChart — BARS, GROUPED BY DAY, SINGLE PASS
             const sorted = [...expenses].sort((a,b) => a.date.localeCompare(b.date));
             for (const e of sorted) grouped[e.date] = (grouped[e.date] || 0) + e.amount;
             const data = Object.entries(grouped).map(([date, total]) => ({
               date: format(parseISO(date), 'MMM d'), total }));
           Points to make: the input is sorted ascending BEFORE accumulating,
           so the insertion order of the object's keys is chronological; JS
           preserves string-key insertion order for non-numeric keys, so the
           resulting array is already in the right order with no second sort.
           The bucket key is the FULL date, so all expenses on the same day
           collapse into one summed bar.

       (C) TrendLineChart — LINE, GROUPED BY MONTH, SINGLE PASS
           Identical structure, but the bucket key is
             const key = e.date.slice(0, 7);   // YYYY-MM
           and the human label must be built from a SYNTHETIC valid date:
             format(parseISO(`${month}-01`), 'MMM yyyy')
           The "-01" is essential: a bare 'YYYY-MM' is not a reliably
           parseable date, so a day component is appended before parsing.
           Rendered with type="monotone" (smoothed curve), strokeWidth 2, and
           a dot marker at each data point.

       (D) THE COMPARISON TO PUT IN THE REPORT
           DailyBarChart and TrendLineChart are the SAME algorithm at two
           different bucket granularities. That is worth pointing out: the
           lesson is that a well-factored aggregation routine can be reused
           with a single changed parameter (the key expression). By contrast
           CategoryPieChart uses a different, less efficient strategy for the
           same task. This contrast is a good discussion point in an
           "Analysis" or "Critical Review" section.

       (E) EMPTY STATE — all three charts return early with a centred
           "No data to display" message when their data array is empty,
           rather than rendering an empty axis.

13.7  ALGORITHM 7 — CSV EXPORT
       File: src/utils/export.ts   Entirely client-side, five steps.

         1. HEADERS: Date, Description, Category, Amount, Recurring
         2. ROWS: for each expense
              [ e.date, `"${e.description}"`, CATEGORY_LABELS[e.category],
                e.amount.toFixed(2), e.isRecurring ? 'Yes' : 'No' ]
            Note three deliberate choices: the raw category KEY is translated
            to its human LABEL so the file is readable outside the app; the
            amount is fixed to exactly two decimal places so the file never
            contains floating-point artefacts; and the description is wrapped
            in double quotes.
         3. ASSEMBLE: header row + data rows joined with '\n' (LF endings).
         4. DOWNLOAD without a server:
              const blob  = new Blob([csv], { type: 'text/csv' });
              const url   = URL.createObjectURL(blob);
              const a     = document.createElement('a');
              a.href = url;
              a.download = `expenses-${new Date().toISOString().split('T')[0]}.csv`;
              a.click();
              URL.revokeObjectURL(url);
            The <a> element is never appended to the DOM — every modern
            browser honours a programmatic click on a detached anchor.
            The filename is date-stamped, so repeated exports on the same day
            produce distinguishable files.
            revokeObjectURL is called immediately to release the underlying
            blob, which prevents a memory leak — a small detail that shows
            correct resource management.
         5. SCOPE: it exports the CURRENTLY FILTERED SET (Expenses.tsx passes
            `filtered`), not the whole database. This is the right default —
            the export matches what the user is looking at — but it must be
            documented, because a user who has a filter applied will get a
            partial file without being warned.

         KNOWN GAP (Limitation L-13): the only escaping applied is wrapping
         the description in double quotes. A description containing a double
         quote or a newline would corrupt the file, and the category label is
         not quoted at all. A correct implementation would replace every
         embedded quote with two quotes, per RFC 4180, and quote any field
         that contains a comma, a quote or a newline. The fix is three lines
         and is given as Future Work F-05.

13.8  ALGORITHM 8 — CURRENCY FORMATTING
       File: src/hooks/useFormatCurrency.ts

       useFormatCurrency() — returns a MEMOISED formatting function
         new Intl.NumberFormat('en-US', {
           style: 'currency', currency, minimumFractionDigits: 2
         }).format(amount)
       The Intl.NumberFormat object is expensive to construct, so it is
       created inside a useCallback keyed on [currency]. Changing the
       currency in Settings invalidates the callback and therefore re-formats
       every value across the entire application immediately. No currency
       library is used; this is the browser's own locale-aware formatter.

       useCurrencySymbol() — extracts JUST the symbol
         new Intl.NumberFormat('en-US', { style: 'currency', currency })
           .formatToParts(0)
           .find(p => p.type === 'currency')?.value ?? '$'
       WHY THIS EXISTS: Recharts' Y-axis tick formatter wants a compact
       "$450" label, not a full "USD 450.00" string, so the axis needs the
       bare symbol. Formatting the number 0 and picking out the part whose
       type is 'currency' is a neat, dependency-free way to get it, and it
       correctly yields $, EUR-sign, GBP-sign, the yen sign, the rupee sign,
       and the prefixed forms C$ and A$. The `?? '$'` fallback prevents a
       crash on an unexpected locale.

SECTION 14 : NOTABLE IMPLEMENTATION TECHNIQUES
================================================================================
  These fourteen techniques are the concrete engineering highlights. Each one
  is a good candidate for a sub-heading in the Implementation chapter, because
  each demonstrates a specific, defensible technical decision.

14.1  HYBRID STYLING: TAILWIND CLASSES PLUS TWO INLINE STYLES
       Almost everything is styled with Tailwind `className` strings, but
       exactly two components use inline `style` — and each for a reason that
       Tailwind cannot solve. Discussing the boundary between the two is a
       strong sign of understanding.

       CASE A — Runtime-computed colour (components/ui/Badge.tsx)
         Tailwind's class generation works by scanning source files for
         complete class-name strings. It CANNOT generate a class from a value
         that only exists at runtime, so a badge whose colour comes from
         CATEGORY_COLORS cannot be styled with utility classes.
         The component therefore computes the colour and applies it inline:
           style={{ backgroundColor: `${color}18`, color: color }}
         The `18` suffix is the elegant part. CATEGORY_COLORS holds 6-digit
         hex values, and appending a two-digit alpha channel to a hex string
         produces an 8-digit hex with that alpha — `18` in hex is 24/255, so
         the badge background is a ~9% tint of the category colour. One string
         concatenation gives a themed translucent background with no colour
         library, no opacity utility and no CSS variable. A 1.5x1.5 dot span
         carries the full-saturation colour.

       CASE B — Runtime-computed geometry (components/ui/ProgressBar.tsx)
         The fill width is a percentage derived from data, so it is set with
         `style={{ width: `${pct}%` }}` while the shape, colour, rounding and
         transition remain Tailwind classes.

       THE CONTRAST WORTH EXPLAINING: ProgressBar's colour is ALSO
       data-dependent, yet it uses Tailwind classes ('bg-red-500' etc.)
       rather than inline styles. The reason is that the three possible
       colours are complete literal strings present in the source, so
       Tailwind's scanner finds them and emits the CSS — whereas a category
       colour is only known at runtime. Same problem, two valid solutions,
       chosen on the basis of whether the value is knowable at build time.
       This is a genuinely good discussion point.

14.2  THE REUSABLE DESIGN SYSTEM: EXTEND THE DOM, DON'T WRAP IT
       The four form/surface primitives follow one consistent pattern:
         1. INTERFACE EXTENSION — the props interface extends the native
            element's own React interface, so the whole native API is
            inherited with full type safety and nothing needs reimplementing.
              ButtonProps extends ButtonHTMLAttributes<HTMLButtonElement>
              InputProps  extends InputHTMLAttributes<HTMLInputElement>
              SelectProps extends SelectHTMLAttributes<HTMLSelectElement>
              CardProps   extends HTMLAttributes<HTMLDivElement>
         2. OPTIONAL ADDITIONS — a small number of domain-specific props
            (`variant`, `size`, `label`, `error`, `options`).
         3. REST + SPREAD — destructure the custom props, then `{...props}`
            the remainder onto the native element.
         4. `className` LAST — the incoming className is interpolated LAST in
            the template literal, so a caller can always override the base
            styles. This is what lets Dashboard override Card's padding
            (`px-4 py-4 md:px-6 md:py-6`) and inject `flex items-center gap-3`
            into StatCard.
       Modal.tsx is the deliberate exception: it declares a hand-written
       interface because it needs no native attribute passthrough.

14.3  BUTTON VARIANT AND SIZE SYSTEM
       `variants` and `sizes` are plain constant objects of class strings, and
       the component indexes them with the prop. 4 variants (primary,
       secondary, danger, ghost) x 3 sizes (sm, md, lg) = 12 combinations from
       37 lines, with `variant = 'primary'` and `size = 'md'` as defaults.
       Every variant includes its own hover, disabled and dark-mode states,
       and every button gets a base layer of `inline-flex items-center
       justify-center gap-2 rounded-lg font-medium transition-colors
       cursor-pointer disabled:cursor-not-allowed`. Keep buttons visually
       identical everywhere by always using this primitive — which the
       codebase does, including for the icon-only row actions.

14.4  RESPONSIVE DESIGN: ONE COMPONENT, TWO NAVIGATION PARADIGMS
       Rather than building two layouts, the SAME markup serves both, with
       Tailwind prefixes deciding what is visible:
         - Below `md`: the sidebar is translated off-canvas and a fixed
           bottom tab bar appears (`md:hidden`); the main column gets
           `pb-16` to clear it.
         - At `md` and above: the sidebar is forced visible and in normal flow
           (`md:static md:translate-x-0`), and the bottom bar is removed.
       Additional responsive behaviour worth describing:
         - Dashboard's KPI grid: grid-cols-1 -> sm:grid-cols-2 -> lg:grid-cols-4
         - Dashboard's / Reports' chart grid: 1 -> lg:grid-cols-2
         - Forms: `grid-cols-1 sm:grid-cols-2` so amount and category sit
           side by side on wider screens
         - Typography scales at `md` (e.g. `text-lg md:text-xl` on the page
           title, `text-lg md:text-2xl` on a StatCard value)
         - ICONS ALSO SCALE: `size={20} className="md:size-6"` — a small
           detail that materially affects perceived quality
         - Button text is hidden below `sm`, leaving the icon
         - Charts use Recharts ResponsiveContainer at width 100%, height 300
       This satisfies NFR-02 with no JavaScript and no media-query queries
       written by hand.

14.5  DARK MODE WITHOUT A FLASH
       Dark mode is the one feature that has to be solved in two places,
       because the store is not available before React runs.
       STEP 1 — a small SYNCHRONOUS inline <script> in <head>, before any
         stylesheet is applied:
           try {
             var s = JSON.parse(localStorage.getItem('expense-tracker-store') || '{}');
             if (s && s.state && s.state.theme === 'dark')
               document.documentElement.classList.add('dark');
           } catch (e) {}
         This runs before first paint, so a dark-mode user never sees a white
         flash. The try/catch means a corrupted or hand-edited localStorage
         value degrades gracefully to light mode instead of throwing.
       STEP 2 — the class must be kept in sync afterwards. AppLayout has the
         single useEffect that watches the theme slice:
           useEffect(() => {
             document.documentElement.classList.toggle('dark', theme === 'dark');
           }, [theme]);
         The inline script and this effect together mean the class is correct
         both before AND after hydration. Having exactly one effect own the
         DOM class means there is no possibility of two components fighting
         over it.
       STEP 3 — the class must be what Tailwind keys off, which requires
         redefining the dark variant in index.css (see Section 15.2).

14.6  FORM VALIDATION WITH A FIELD-TO-MESSAGE ERROR MAP
       Instead of a boolean per field, ExpenseForm keeps
       `errors: Record<string, string>` — a map from field name to message.
       The map is built by one validate() function and consumed directly by
       the primitives: `<Input error={errors.amount} />` and the Input renders
       both a red border and the message. `Object.keys(errs).length === 0` is
       the gate. This scales to any number of fields without adding any
       per-field state, and it is the difference between a usable form and a
       silent one. Admit that validation is on-submit only — there is no
       live re-validation and no focus management to the first invalid field.

14.7  THE SEARCH-IN-ICON-OVERLAP TECHNIQUE
       ExpenseFilters positions a Search icon over the input:
         <Search size={18} className="absolute left-3 top-1/2 -translate-y-1/2 text-gray-400" />
         <input className="... pl-10 ..." />
       The icon is absolutely positioned and vertically centred by
       `-translate-y-1/2`, and the input's `pl-10` (2.5rem) reserves the
       space. Worth a one-line mention as a pure-CSS solution that avoids
       wrapper markup.

14.8  RESPONSIVE ROW LAYOUT THAT ACTUALLY SURVIVES LONG TEXT
       ExpenseList composes three utilities to stop a long description from
       breaking the row: `min-w-0` on the flexible text column (without it a
       flex child refuses to shrink below its content), `truncate` on the
       description (single-line ellipsis), and `shrink-0` on the amount and
       action buttons (so the money and the delete button can never be
       squeezed). This is the standard flexbox-overflow triple and it is the
       difference between a list that looks right and one that overflows on a
       320 px screen.

14.9  THE CONFIG-DRIVEN SELECT
       Select takes `options: { value: string; label: string }[]`, a shape
       deliberately decoupled from the domain types. One component then serves
       seven different purposes: the currency list, the expense category, the
       recurring interval, the budget category, the filter category, the sort
       key and the sort order. The "All Categories" option is expressed as
       `{ value: '', label: 'All Categories' }`. It is a NATIVE <select>, not
       a custom listbox — a deliberate accessibility and cross-platform
       choice (native pickers on mobile are good). The honest cost of this
       design: because option values are plain strings, callers must cast at
       the boundary (`as Category`, `as 'date' | 'amount' | 'category'`).
       The report can note that a generic component parameterised by the
       option value type would remove those casts — a good "what I would
       improve" observation.

14.10  MODAL AS A MOBILE BOTTOM SHEET
       One Modal component serves both form platforms with a single
       breakpoint switch: `items-end` + `w-full` + `rounded-t-xl` (and only
       top corners rounded) below `md`, becoming `md:items-center` +
       `md:max-w-lg` + `md:rounded-xl` + `md:p-6` above it. It uses
       conditional UNMOUNTING (`if (!open) return null;`) rather than
       `hidden` or opacity, so a closed modal contributes nothing to the DOM
       or to the accessibility tree. Two close affordances are provided:
       clicking the backdrop, and an X button. The panel is layered above the
       backdrop with `relative z-10` inside a `z-50` container.

14.11  THE TRANSFORM-BASED DRAWER
       Sidebar.tsx keeps the <aside> permanently in the DOM and animates it
       with a class toggle between `translate-x-0` and `-translate-x-full`
       plus `transition-transform duration-300`. The advantages over
       conditional rendering are smoother animation (a CSS transition the
       compositor can handle) and preservation of internal state across
       open/close. A conditional backdrop is rendered for click-to-close,
       guarded with `md:hidden` so it can never intercept clicks on desktop.
       The sidebar is intentionally dark (bg-gray-900) in BOTH themes.

14.12  ACCURATE, CONTEXTUAL ACCESSIBLE NAMES ON ROW ACTIONS
       ExpenseList is the one place accessibility was done carefully: both
       icon-only buttons carry labels built from the record itself —
         aria-label={`Edit ${expense.description}`}
         aria-label={`Delete ${expense.description}`}
       So a screen reader announces "Delete Lunch", not "button". Include this
       as a positive example, and then honestly note that the same treatment
       is missing from the icon-only buttons in Header.tsx, Modal.tsx and
       BudgetProgress.tsx (Limitation L-09).

14.13  DATA-DEPENDENT EMPTY STATES
       Empty state is not a single generic message. ExpenseList branches:
         expenses.length === 0  -> "Add your first expense to get started"
         otherwise               -> "Try adjusting your filters"
       The distinction between "you have no data" and "your filters are too
       narrow" is what makes an empty list feel considered rather than broken.
       All three charts share a centred "No data to display" panel, and
       BudgetProgress has its own "No budgets set for this month. Add one
       above!" message. Buttons that would produce an empty result are
       disabled instead of failing — the Export CSV button is
       `disabled={filtered.length === 0}`.

14.14  DISABLING DESTRUCTIVE ACTIONS SAFELY
       Settings' "Clear All Data" is the only irreversible operation, so it
       gets three defences: it lives in a visually separated "Danger Zone"
       section with a red heading; the button uses the `danger` variant; and
       its subtitle interpolates the live count ("Permanently delete all N
       expenses and budgets") so the consequence is explicit BEFORE the
       click. A native window.confirm() then guards the action. Use this to
       introduce the contrast with the per-row delete in ExpenseList, which
       is immediate and has no confirmation (Limitation L-16).

SECTION 15 : USER INTERFACE AND DESIGN SYSTEM

15.1  STYLING APPROACH
       Utility-first, className-driven, with exactly one CSS file in the
       entire project (src/index.css, 22 lines). There are no CSS Modules, no

15.2  THE STYLESHEET, LINE BY LINE  (src/index.css — useful verbatim for the
       report's "Design Implementation" section)

       @import "tailwindcss";
         The Tailwind v4 entry point. V4 scans the project for class usage
         automatically, so no `content` array is required.

       @custom-variant dark (&:where(.dark, .dark *));
         REDEFINES HOW DARK MODE ACTIVATES. By default Tailwind's `dark:`
         variant keys off the operating system's `prefers-color-scheme` media
         query. This line switches it to a CLASS strategy, so dark mode
         becomes an explicit user choice stored in the app's own state rather
         than an OS setting the user cannot control from inside the app. This
         one line is what makes the manual theme toggle possible.

       @theme { --color-primary: #6366f1; --color-primary-dark: #4f46e5;
                --color-primary-light: #a5b4fc; --color-secondary: #ec4899;
                --color-success: #22c55e; --color-warning: #f59e0b;
                --color-danger: #ef4444; }
         Tailwind v4's CSS-variable design-token API, which would generate
         utilities such as `bg-primary` and `text-danger`.
         IMPORTANT HONESTY POINT (Limitation L-03): these seven tokens are
         declared but NEVER USED. Every component uses stock Tailwind palette
         utilities instead — `bg-indigo-500`, `text-red-500`, `bg-gray-200`,
         `dark:bg-gray-800`, `text-emerald-500` and so on. The project
         therefore has two parallel, unconnected colour systems: a declared
         token set and the palette actually in use. The report may present
         this as "a design-token layer was established in anticipation of
         theming, and wiring the components to it is the first item of
         future work" — which is truthful and shows the token system's
         purpose. Do NOT claim a working themed design system.

       body { margin: 0;
              font-family: 'Inter', system-ui, -apple-system, sans-serif; }
         Minor issue (Limitation L-15): 'Inter' is never loaded — there is no
         @font-face rule and no Google Fonts <link> — so the browser silently
         falls back to system-ui. Also note the deliberate omission of a
         font preconnect/preload, which is a legitimate performance choice
         but means the Inter entry is currently dead.

       #root { min-height: 100vh; }
         Makes the React root fill the viewport so the layout's
         `min-h-screen` background covers the whole page.

SECTION 16 : DATA PERSISTENCE
================================================================================

16.1  MECHANISM
     Zustand's `persist` middleware, configured with a single option:
       persist((set) => ({ ... }), { name: 'expense-tracker-store' })
     With no `storage` override, the default is the browser's localStorage;
     with no custom serialiser, the default is JSON.stringify /
     JSON.parse. The middleware subscribes to the store and writes the whole
     state object on every change, and rehydrates from it on page load.

16.2  THE STORAGE KEY AND WHY IT IS NAMED EXPLICITLY
     The key is 'expense-tracker-store'. It is named explicitly rather than
     left to a default because index.html's pre-paint theme script must read
     the SAME key before any JavaScript module loads. The two places must
     agree; the string is therefore a shared contract between the store and
     the HTML shell. Say this in the report — it explains a non-obvious line
     of the HTML.

16.3  WHAT IS AND IS NOT PERSISTED
     PERSISTED: expenses, budgets, filters, theme, currency.
     NOT PERSISTED: modal open/closed state, which row is being edited, the
     mobile drawer's open state. These are correctly left as ephemeral local
     component state — persisting them would mean the app reopened with a
     dialog already on screen.

16.4  WHY localStorage IS A DEFENSIBLE CHOICE HERE  (report subsection)
     ADVANTAGES ACTUALLY ENJOYED BY THIS PROJECT
       - SYNCHRONOUS. The store is fully populated before the first render, so
         there is no loading spinner, no skeleton screen, no "flash of empty
         UI", and no async state to model. This is the single biggest
         practical advantage over IndexedDB (which is async) or a network
         fetch.
       - Simplicity. Five lines of middleware config, no transaction or
         schema-management layer.
       - Adequate capacity. The roughly 5 MB per-origin quota is orders of
         magnitude more than a personal expense record needs; a few thousand
         records at roughly 200 bytes each is well under 1 MB.
       - Privacy. Data never leaves the origin.
     HONEST LIMITATIONS OF THE CHOICE
       - Access is SYNCHRONOUS and on the MAIN THREAD, so it can jank if a
         very large dataset is ever written.
       - It is a STRING store, so every read parses JSON and every write
         serialises the WHOLE state — a full rewrite per mutation. Fine at
         this scale, not at a large one.
       - It has NO QUERY CAPABILITY, no indexes and no partial reads.
       - It is per-BROWSER-PROFILE, so data does not follow the user to
         another device or browser, and private/incognito windows lose it.
       - It is trivially editable by the user through developer tools, and
         there is no encryption at rest.
       - Clearing site data destroys the records, which is exactly why the CSV
         export and the explicit "N expenses" count in the Danger Zone matter.
     Recorded in the report as a considered trade-off, with IndexedDB as the
     documented upgrade path (Future Work F-04).

16.5  DATA LIFECYCLE
       CREATE: form submit -> store action generates uuid + timestamp ->
               prepend -> persist writes localStorage.
       READ:   on page load, persist rehydrates synchronously -> selectors
               subscribe -> derived values computed during render.
       UPDATE: form submit with editExpense -> store merges by id -> persist.
       DELETE: row button -> store filters by id -> persist. Immediate, no
               confirmation, no undo.
       EXPORT: utils/export.ts serialises the filtered array to CSV and
               triggers a browser download.
       DESTROY: Settings -> window.confirm -> clearAll() empties expenses and
               budgets (theme and currency survive) -> persist writes the
               smaller payload.

17.4  TYPESCRIPT CONFIGURATION
     THREE-FILE PROJECT-REFERENCE SETUP (modern recommended layout):
       tsconfig.json      — solution-style root: "files": [] and two
                            references. Exists only so that `tsc -b` can
                            build both sub-projects in order.
       tsconfig.app.json  — governs everything under src/.
       tsconfig.node.json — governs vite.config.ts only, with lib: ES2023
                            (no DOM) and types: ["node"].
     Separating the tool config from the application config means the DOM
     types are not in scope when type-checking the build script, and
     incremental build info is cached separately for each — which is what
     makes `tsc -b` fast on repeat builds.
     Key compiler options and what they contribute:
       target / lib            ES2023 + DOM.
       module / moduleResolution  esnext + "bundler" — resolution semantics
                              that match how a bundler actually loads code.
       jsx                     "react-jsx" — the automatic runtime, so no
                              `import React` is needed in any file.
       noEmit                  true — tsc only type-checks; Vite does the
                              emitting.
       verbatimModuleSyntax    true — type-only imports MUST use
                              `import type`, so they are erased entirely and
                              the emitted bundle is smaller. The codebase
                              follows this consistently.
       erasableSyntaxOnly      true — forbids TypeScript `enum`, `namespace`
                              and constructor parameter properties, keeping
                              every construct convertible to plain JavaScript.
                              This is what pushed the category model to a
                              string-literal union (Section 9.1b).
       noUnusedLocals         true — unused variables are a build error.
       noUnusedParameters      true — unused parameters are a build error.
       noFallthroughCasesInSwitch  true — a missing break is a build error.
       allowImportingTsExtensions   true — permits explicit `./App.tsx`
                              specifiers, which main.tsx uses.
       skipLibCheck            true — do not type-check node_modules.
       types                   ["vite/client"] — provides import.meta.env etc.
     HONEST CAVEAT (Limitation L-20): `strict` is NOT explicitly enabled in
     tsconfig.app.json. The individual strict-adjacent options listed above
     are set, and the project is fully typed, but the full strict family
     (strictNullChecks, noImplicitAny, strictFunctionTypes, and the
     strictFunctionTypes-related exactOptionalPropertyTypes and
     noUncheckedIndexedAccess) is not. Enabling `strict` is the first item of
     Future Work F-07 and would be a credible, concrete improvement to
     discuss.

18.2  THE REFACTORING PHASE  (a real, presentable development narrative)
     After the initial working baseline, ten files were modified and one new
     utility was extracted. The change set is a coherent, single-theme
     cleanup and is worth describing as "the optimisation and DRY pass" in
     the report's "Development Methodology" or "Issues Faced and Resolved"
     chapter.

     CHANGE 1 — EXTRACTED A DATE UTILITY MODULE  (new file src/utils/date.ts)
       Previously, date-key construction was scattered: Dashboard.tsx used
       date-fns' `subMonths(new Date(), 1).toISOString()` to derive the
       previous month, and other modules built month keys inline. A dedicated
       module now provides todayISO(), currentMonthKey(), monthKeyOf() and
       prevMonthKey(), all in local time, all producing zero-padded
       lexicographically-sortable keys. Benefit: one place defines the date
       format, and the month-overflow edge case is handled once
       (Section 13.3b) instead of at each call site.

     CHANGE 2 — REMOVED A DEAD UTILITY
       `getMonthRange(dateStr)` in utils/filter.ts used date-fns'
       startOfMonth/endOfMonth to build a {start, end} pair. Nothing called
       it. It also mixed time zones by calling toISOString() on a local Date.
       Deleted. (Related to Limitation L-06, since this was the only code
       that could have driven a date-range filter.)

     CHANGE 3 — REMOVED FORMATTING HELPERS THAT DUPLICATED A HOOK
       utils/format.ts previously exported formatCurrency(), formatMonth() and
       formatDay(). formatCurrency() duplicated the logic already provided,
       and more correctly, by useFormatCurrency.ts — a hook that reads the
       currency from the store and memoises the Intl.NumberFormat instance.
       The two `formatMonth`/`formatDay` helpers were superseded by date-fns'
       `format()` called inline inside the chart components. format.ts was
       reduced from 21 lines to 4, leaving only formatDate(). The result is
       that ALL currency formatting in the project now goes through one hook,
       so a currency change can never be missed by a component using a
       bypassed helper. This is the single best "issue found and resolved"
       story in the project: duplication that risked a functional bug was
       removed in favour of one source of truth.

     CHANGE 4 — REPLACED AN O(k*n) ALGORITHM WITH AN O(n) ONE
       Dashboard's top-category calculation previously ran, for every expense,
       a full filter+reduce over the entire month array — a nested loop. It
       now builds a single totalsByCategory map in one pass and then takes the
       maximum over the fixed CATEGORIES list. The accumulator's seed changed
       from `{ category: '', amount: 0 }` to `{ category: null, amount: 0 }`,
       which makes the "no data" case representable, and the result is now
       rendered as CATEGORY_LABELS[topCategory.category] rather than the raw
       key, so the user sees "Food & Dining" instead of "food". The runtime
       of the calculation dropped from O(n^2)-ish to O(n).

     CHANGE 5 — CONSISTENT IMPORTS AND A COPY FIX
       The budget components and ExpenseForm were updated to import the shared
       date helpers, and AppLayout was tidied.

     CHANGE 6 — REMOVED AN UNUSED PWA PLUGIN DEPENDENCY
       `vite-plugin-pwa` was removed from devDependencies. It was never
       imported and never configured (there is no manifest and no Service
       Worker). Its removal is honest: the project has no offline-caching or
       installable-PWA capability. This is why the report must not claim PWA
       support (Limitation L-18). Equally, `framer-motion` is still declared
       but unused (Limitation L-01) and four testing packages are declared but
       unused (L-02) — so in the report's "cleaning up dependencies" story,
       be precise: one unused dependency was removed, others remain as
       identified future work.

     CHANGE 7 — DESCRIPTION TEXT EDIT
       The meta description was changed from "a fast, offline-ready expense
       tracker..." to "a fast expense tracker...", removing the word
       "offline-ready" because the app has no Service Worker and therefore no
       installable offline caching. A small, honest instance of not claiming
       more than the code delivers — worth mentioning as a documentation-
       accuracy fix.

19.4  KNOWN BUGS TO REPRODUCE AND CONFIRM BEFORE WRITING ABOUT THEM
     (Verifying these yourself is what makes the Limitations chapter credible.)
     B-1  Chart colours ignore the theme. All three charts hardcode
          stroke="#374151" for the grid, stroke="#9ca3af" for the axes and
          stroke/fill="#6366f1" for the series. In dark mode these do not
          respond to the `.dark` class, so the grid and axes are dark grey on
          a dark card. Confirm visually, then report as Limitation L-19 with
          a screenshot — it is the clearest visual defect in the app.
     B-2  There is no catch-all route, so a mistyped URL such as /expens
          renders a blank white page with no message.
     B-3  A long description containing a double quote or a newline produces
          a malformed CSV (only the field is quoted, never escaped).
     B-4  The X-axis labels of the bar chart overlap when many distinct dates
          are present, because no tick `interval` is configured.
     B-5  On the Budget screen, `removeBudget` types its first parameter as
          `string` rather than `Category | 'overall'`, a small type-safety
          looseness compared with the rest of the store.
     B-6  The Reports page's third card is titled "Daily Spending" but plots
          EVERY date in the entire history, not one month — a label that
          slightly misdescribes the data.
     B-7  The "Add Expense" and "Export CSV" buttons hide their text below the
          `sm` breakpoint, leaving icon-only controls with no accessible name.
     B-8  A description containing a comma is wrapped in quotes so it is safe,
          but a CATEGORY LABEL is not quoted at all; this is only safe today
          because no label contains a comma — a latent bug if labels change.

================================================================================
SECTION 20 : LIMITATIONS  (use this for the "Limitations" / "Issues Faced"
          chapter — every item is real, verifiable in the code, and has a
          corresponding fix in Section 21)
================================================================================

  Present these honestly. A report that identifies and analyses its own
  limitations is graded far better than one that claims perfection. Where an
  item was discovered and partly addressed during development, say so.

L-01  UNUSED ANIMATION DEPENDENCY
       `framer-motion` (13.1.1) is declared in dependencies but is imported
       nowhere in src/. It contributes nothing except install weight and a
       false implication in package.json. Cause: it was added in anticipation
       of page/list transitions that were never implemented.
       IMPACT: low functional impact, but it misrepresents the dependencies
       in use. FIX: F-09.

L-02  NO AUTOMATED TEST SUITE
       Zero test files, no `test` script, no test-runner configuration — while
       four testing packages (vitest, jsdom, @testing-library/react,
       @testing-library/jest-dom) sit unused in devDependencies. Cause: the
       testing infrastructure was scaffolded but the tests were never written.
       COMPENSATING CONTROL: the entire build is gated on `tsc -b`, so a type
       error fails `npm run build`; ESLint runs four rule sets including
       rules-of-hooks. The pure functions in src/utils are side-effect-free
       and therefore unit-testable by design. HONEST STATEMENT: correctness
       assurance currently rests on the type system, static analysis and
       manual testing, not on automated tests. FIX: F-01 (top priority).

L-03  DESIGN TOKENS DECLARED BUT NOT CONSUMED
       src/index.css defines seven @theme colour tokens (--color-primary,
       --color-primary-dark, --color-primary-light, --color-secondary,
       --color-success, --color-warning, --color-danger), but no component
       uses the generated utilities. Every component instead uses stock
       Tailwind palette classes (bg-indigo-500, text-red-500, bg-gray-200,
       dark:bg-gray-800, ...). Cause: the token layer was established first
       and the components were then styled directly against the palette.
       IMPACT: two parallel, unconnected colour systems; retheming the app
       would require editing 27 files rather than one theme block.
       HONEST FRAMING: a design-token foundation exists and is unused; wiring
       the components to it is scheduled work. FIX: F-10.

L-04  README IS STILL THE UNMODIFIED VITE TEMPLATE
       README.md (73 lines) is boilerplate from `npm create vite@latest`. It
       is titled "React + TypeScript + Vite" and discusses the React Compiler
       and ESLint configuration. It never mentions XApp, expense tracking, the
       store, the charts, the features, or how to run the project.
       IMPACT: onboarding, documentation quality, and the quality of the
       repository itself. FIX: F-11.

L-05  DUPLICATED AND UNMEMOISED DERIVATION
       On the Expenses screen, `filterExpenses(expenses, filters)` is called
       independently by BOTH pages/Expenses.tsx and components/expenses/
       ExpenseList.tsx. Each is O(n log n). Neither is wrapped in useMemo.
       Compounding this, eight components subscribe to the ENTIRE store
       (`const { expenses, filters } = useStore()`) rather than to atomic
       slices, so any state change re-renders them all.
       IMPACT: the filter pipeline runs twice per render cycle and unrelated
       state changes cause avoidable re-renders. Harmless at personal data
       volumes; a genuine scaling limit. FIX: F-03, F-12.

L-06  DATE-RANGE FILTERING IS IMPLEMENTED BUT UNREACHABLE
       `Filters.dateRange` is a fully specified field, and utils/filter.ts
       implements Stage 1 (isWithinInterval) to honour it. But no UI ever
       sets it: ExpenseFilters has only search, category, sort-key and
       sort-order controls, and nothing dispatches setFilters({ dateRange }).
       A previously existing helper, `getMonthRange()` in utils/filter.ts,
       which would have driven such a control, was removed during
       refactoring as dead code.
       IMPACT: an implemented, tested-by-design capability with no interface.
       HONEST FRAMING: the domain logic is complete and the missing piece is
       purely a control. FIX: F-13.

L-07  PERSISTENCE IS UNVERSIONED, AND PERSISTS UI STATE
       Two related issues in the persist configuration:
       (a) No `version` and no `migrate` option. The stored payload has no
           schema version, so any future change to the Expense or Budget shape
           would silently produce records that fail to load correctly, with no
           migration path.
       (b) No `partialize`, so `filters` is persisted too. The user's last
           search text and sort order therefore survive a reload — arguably
           good UX, but it also means reloading after filtering can look like
           a bug when a stale filter is silently applied.
       FIX: F-06.

L-08  BUDGET UPSERT GIVES NO FEEDBACK
       `setBudget` upserts on (category, month). Re-submitting a budget for a
       category and month that already have one silently overwrites it, with
       no "Budget updated" confirmation and no change in the button label.
       Compare with ExpenseForm, whose button correctly switches between
       "Add Expense" and "Update Expense".
       IMPACT: a user who does not notice may believe they have set two
       budgets when they have set one. FIX: F-14.

L-09  INCOMPLETE ACCESSIBILITY
       Partial only. Good: all controls are native elements (keyboard
       operable by default); ExpenseList's row actions have contextual
       aria-labels ("Delete Lunch"); zoom is not disabled; focus is visible
       on inputs and selects. Missing:
         - Modal has no role="dialog", no aria-modal, no focus trap, no
           Escape-to-close, and its X button has no aria-label.
         - The icon-only buttons in Header (menu, theme) have no aria-label.
         - BudgetProgress's per-category delete buttons have no aria-label.
         - The Sidebar drawer has no Escape handler and no aria-expanded or
           aria-controls on the hamburger button.
         - Input and Select render a <label> with no htmlFor and no matching
           input id, so the label is not programmatically associated with the
           field.
         - Below the `sm` breakpoint the Add / Export / Clear button text is
           hidden, leaving an icon-only control with an empty accessible name.
         - ProgressBar has no role="progressbar" and no aria-valuenow.
         - No skip-to-content link.
       FIX: F-15.

L-10  NO CATCH-ALL (404) ROUTE
       The route table has five exact paths and no `path="*"` fallback. A
       mistyped or stale URL (e.g. /expens) renders a blank page with no
       message and no way back except the browser's back button.
       FIX: F-16.

L-11  CURRENCY SELECTION FORMATS BUT DOES NOT CONVERT
       Changing the currency in Settings re-labels and re-formats every amount
       through Intl.NumberFormat, but the stored numeric value is UNCHANGED.
       There is no exchange-rate table, no rate lookup, and no conversion. A
       user who switches from USD to INR sees the same digits with a different
       symbol — arguably misleading, since the number now implies a different
       real-world value.
       HONEST FRAMING: the setting is a DISPLAY preference, and the report
       must describe it as such. FIX: F-17.

L-12  NO DEPLOYMENT CONFIGURATION, AND A ROUTING CAVEAT
       The repository contains no CI/CD workflow, no Dockerfile, no hosting
       configuration, and no live URL. The production bundle has been built
       locally (dist/ exists) but the project has not been deployed.
       Additionally, because App.tsx uses BrowserRouter (the HTML5 History
       API) rather than HashRouter, a static host MUST be configured to
       rewrite all unknown paths to index.html. Without that, refreshing
       directly on /expenses or /reports returns a 404. This is the single
       most likely deployment pitfall for this project and is worth naming
       explicitly. FIX: F-18.

L-13  CSV ESCAPING IS INCOMPLETE
       utils/export.ts wraps the description in double quotes but applies no
       other escaping. A description containing a double quote or a newline
       will corrupt the file. The category label is not quoted at all, which
       is safe only because no current label contains a comma. Per RFC 4180,
       an embedded quote must be doubled and any field containing a comma,
       quote or newline must be quoted.
       IMPACT: an export can produce a file that a spreadsheet mis-parses.
       The fix is about three lines. FIX: F-05.

L-14  DUPLICATED "SPENT THIS MONTH" DERIVATION
       The identical three-line derivation (filter expenses to the current
       month key, then reduce to a sum) appears in THREE components:
       Dashboard.tsx, BudgetAlertBanner.tsx and BudgetProgress.tsx.
       Related smaller duplications:
         - The navigation array is declared twice: `links` in Sidebar.tsx and
           `bottomLinks` in AppLayout.tsx, differing only in the "/" label
           ("Dashboard" vs "Home").
         - The current-month YYYY-MM key is derived in three different ways
           across the codebase: `getMonthKey(str)` (a 7-character slice) in
           utils/filter.ts, `e.date.slice(0, 7)` inline in TrendLineChart, and
           `currentMonthKey()` in utils/date.ts.
         - BudgetProgress duplicates its card header/footer markup for the
           overall budget and for each category budget, where a small
           `<BudgetRow>` sub-component would remove the duplication.
       IMPACT: a change to the month-bucketing rule would have to be made in
       several places. FIX: F-03, F-19.

L-15  THE DECLARED FONT IS NEVER LOADED
       index.css sets `font-family: 'Inter', system-ui, -apple-system,
       sans-serif`, but there is no @font-face rule and no Google Fonts
       <link> in index.html. The 'Inter' entry is therefore never satisfied
       and the browser always falls back to system-ui.
       IMPACT: purely cosmetic and graceful (the fallback stack is sensible),
       but the declaration is dead and misleading.
       CONTEXT: the absence of a font download is also why the app has no
       external runtime network dependency, which is a genuine advantage —
       so the correct fix is to decide which of the two matters more. FIX: F-20.

L-16  DESTRUCTIVE ACTIONS LACK CONFIRMATION AND UNDO
       Per-row Delete in ExpenseList removes a record IMMEDIATELY on a single
       click, with no confirmation and no undo. By contrast, Settings' Clear
       All Data does use a window.confirm() and states the exact record count
       in its subtitle. The two destructive paths are therefore inconsistent,
       and the more frequent one is the unprotected one.
       IMPACT: an accidental tap permanently deletes a record.
       FIX: F-21.

L-17  UNREFERENCED STATIC ASSET
       public/icons.svg (5,031 bytes) is copied into the production build but
       is referenced by neither the source nor index.html. It is dead weight
       in dist/. FIX: F-09 (bundle with L-01's cleanup).

L-18  NO PWA / SERVICE WORKER / OFFLINE CACHING
       There is no manifest, no Service Worker, and no offline asset caching.
       The application works with no network connection only AFTER the page
       has been loaded in that session; a cold offline start cannot work,
       because the browser must first fetch index.html and the bundle.
       NOTE: `vite-plugin-pwa` was in devDependencies and has been REMOVED
       during the refactoring phase, and the meta description was edited to
       drop the word "offline-ready" for the same reason. The report must
       therefore describe the offline claim precisely: "no runtime network
       dependency", not "installable offline application". FIX: F-22.

L-19  CHART COLOURS IGNORE THE THEME
       All three chart components hardcode their colours as literal hex values:
         <CartesianGrid stroke="#374151" />   (grid)
         <XAxis stroke="#9ca3af" />  <YAxis stroke="#9ca3af" />  (axes)
         stroke/fill="#6366f1"                (the data series)
       None of these responds to the `.dark` class, because they are SVG
       attributes rather than CSS classes. In dark mode the grid and axes
       stay dark grey on a dark card, producing poor contrast.
       This is the clearest visual defect in the application and the easiest
       to demonstrate. CAUSE: Recharts' stroke/fill props accept CSS colour
       values, so they can be fed `currentColor` or a CSS custom property
       driven by the `.dark` class — the fix is straightforward.
       FIX: F-23.

L-20  `strict` MODE IS NOT EXPLICITLY ENABLED
       tsconfig.app.json sets several individual strict-adjacent options
       (noUnusedLocals, noUnusedParameters, noFallthroughCasesInSwitch,
       erasableSyntaxOnly) but does not set `strict: true`, so
       strictNullChecks and noImplicitAny are not enforced. The codebase is
       fully typed, but full strictness is not guaranteed by the build.
       HONEST FRAMING: type safety is a stated objective (O10) and is
       substantially met through the build gate; enabling `strict` is the
       natural next step. FIX: F-07.

  OPTIONAL OBSERVATIONS (safe to include, good for a "Critical Review")
  O-a  The X-axis of the bar chart has no tick `interval`, so with many
       distinct dates the "Mar 4" labels overlap. Recharts' `interval={n}`
       would fix it.
  O-b  BudgetAlertBanner computes `totalSpent / overallBudget.amount` with no
       zero-denominator guard, whereas ProgressBar guards the identical
       division with `max > 0 ? ... : 0`. It is safe today only because
       BudgetForm rejects amounts <= 0. The same formula should carry the
       same guard in both places.
  O-b2 `removeBudget` declares its first parameter as `string` instead of
       `Category | 'overall'`, which is looser than the model it operates on.
  O-c  The search field dispatches `setFilters` on every keystroke with no
       debounce. At personal data volumes this is correct and simple, but it
       re-runs the pipeline per character.
  O-d  The Sort Order select's option labels ("Newest First" / "Oldest
       First") are date-centric even when the active sort key is Amount or
       Category.
  O-e  The Reports page's third card is titled "Daily Spending" but plots
       every date in the entire history, not one month.
  O-f  Chart components are not memoised and have no loading/empty animation;
       the aggregation re-runs on every render.
  O-g  The production bundle is a single ~676 KB uncompressed JavaScript file
       with no code splitting and no route-level lazy loading. Recharts and
       the icon set account for most of it.
  O-h  CategoryPieChart uses an 8-pass O(k·n) grouping while the two other
       charts use a single O(n) pass — an internal inconsistency in approach.
  O-i  The value "Transactions" on the Dashboard counts this month's records
       only, while the Reports page operates on all history. The Dashboard
       therefore has no "total records ever" figure.
  O-j  The `defaultFilters` object is a shared module-level reference reused
       by `resetFilters`. It is safe today because no code mutates a Filters
       object in place (`setFilters` always spreads), but it is a subtle
       shared-mutable-reference pattern.

SECTION 21 : FUTURE SCOPE / ENHANCEMENTS
================================================================================
  Each item maps to a limitation or an observation from Section 20. Frame
  these as planned work, not as things the project already does. Ordering is
  by value delivered.

  F-01  UNIT AND COMPONENT TESTS  (addresses L-02)  — HIGHEST PRIORITY
        Add vitest with a jsdom environment. First targets, in order of value:
          - utils/filter.ts: the four-stage pipeline — empty filters, each
            filter in isolation and in combination, and the asc/desc
            comparator for all three sort keys.
          - utils/date.ts: month-boundary cases, including 31 January minus
            one month, and a leap-year 29 February.
          - utils/export.ts: a description containing a comma, a double quote
            and a newline.
          - store/useStore.ts: add/update/delete/upsert/clearAll transitions
            and the invariant that addExpense ignores a caller-supplied id.
          - components/expenses/ExpenseForm.tsx: required-field validation and
            create-versus-edit submission, with Testing Library.
        Expected benefit: the type system proves shapes, but only tests prove
        BEHAVIOUR.

  F-02  OPTIONAL BACKEND AND CROSS-DEVICE SYNC  (addresses the scope limit)
        Add a REST or Firebase backend with authentication so that data
        follows the user across devices. Requires: a real data model with
        surrogate keys, an auth flow, conflict resolution for offline edits,
        and a decision about encrypting financial data at rest. This is the
        natural next major version and is the correct answer to "why is your
        data only on one device?".

  F-03  CENTRALISE THE AGGREGATION LOGIC  (addresses L-05, L-14, O-h)
        Introduce a single memoised `useExpensesByMonth()` /
        `useTotalsByCategory()` hook (or a `groupBy` utility) and consume it
        from Dashboard, BudgetAlertBanner, BudgetProgress and all three
        charts. This collapses four duplicate derivations, makes every
        aggregation O(n) single-pass, and gives one place to add memoisation
        and shallow-equality selectors. Highest code-quality return per line
        of effort.

  F-04  MIGRATE TO INDEXEDDB  (addresses Section 16.4)
        Move persistence to IndexedDB via a small wrapper (idb-keyval or
        Dexie) when the data volume justifies it. Benefits: asynchronous so
        the main thread is not blocked; large binary storage, which unlocks
        receipt images; and indexed queries instead of full-array scans.
        Costs to plan for: the store becomes async, so rehydration needs
        handling and a loading state must be designed in.

  F-05  PROPER CSV ESCAPING AND JSON BACKUP IMPORT  (addresses L-13)
        Implement RFC 4180 escaping: double every embedded quote, and quote
        any field containing a comma, quote or newline. Add a "Back up to
        JSON" download and a matching "Restore from JSON" file input, so that
        a user whose site data is cleared can recover. Also add a UTF-8 BOM
        so Excel opens non-ASCII characters correctly.

  F-06  VERSIONED PERSISTENCE WITH MIGRATION  (addresses L-07)
        Add `version` and a `migrate` function to the persist options so the
        stored payload carries a schema version and can be upgraded in place.
        Also add `partialize` to exclude `filters` from what is written.

  F-07  ENABLE TYPESCRIPT strict MODE  (addresses L-20)
        Turn on `strict: true` and fix the resulting errors — most likely in
        the three places that cast strings at select boundaries and in
        `removeBudget`'s parameter type. Consider additionally enabling
        `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.

  F-08  PERFORMANCE: LAZY LOADING AND BUNDLE SPLITTING
        Lazy-load the three chart components with React.lazy and Suspense, so
        the ~676 KB Recharts payload is only fetched when a chart-bearing
        screen is opened. Add manual vendor chunking, and consider swapping
        the icon library for per-icon imports if the bundle audit justifies
        it. Measure before and after with the real build output.

  F-09  DEPENDENCY AND ASSET CLEANUP  (addresses L-01, L-17)
        Remove framer-motion if animations are not implemented; if they are,
        actually use it for modal and list transitions. Delete the
        unreferenced public/icons.svg. Add a dependency-audit note to the
        README.

  F-10  WIRE UP THE DESIGN TOKENS  (addresses L-03)
        Replace the hardcoded palette utilities with the utilities generated
        from the existing `@theme` block (bg-primary, text-danger, and so on),
        or expand the `@theme` block to cover the neutral scale actually in
        use. Either way, end with ONE colour system. This also unlocks
        user-selectable accent colours.

  F-11  WRITE A REAL README  (addresses L-04)
        Replace the Vite boilerplate with: a project description, a feature
        list, a screenshot, the run/build/lint commands, the project
        structure, the technology choices with one-line justifications, and a
        section documenting the known limitations from Section 20.

  F-12  MEMOISATION AND SELECTOR HYGIENE  (addresses L-05, O-f)
        Wrap the expensive derived values in useMemo, and convert the
        whole-store subscriptions to atomic selectors. Where a selector
        returns a new array or object, use a shallow-equality comparator so
        the component does not re-render on every store change.

  F-13  ADD THE DATE-RANGE FILTER UI  (addresses L-06)
        Add two <input type="date"> controls to ExpenseFilters that dispatch
        `setFilters({ dateRange: [start, end] })`. The domain logic, the type
        and the filter stage already exist — only the control is missing. This
        is a small change with an immediately visible benefit.

  F-14  FEEDBACK ON BUDGET UPSERT  (addresses L-08)
        Have `setBudget` report whether it inserted or updated (for example by
        returning a boolean from the action), and show a brief success toast
        saying "Budget updated" versus "Budget created". A lightweight toast
        utility would also serve the delete action.

  F-15  COMPLETE THE ACCESSIBILITY PASS  (addresses L-09)
        Add role="dialog", aria-modal, aria-labelledby and a focus trap plus
        Escape-to-close to Modal; add aria-label to every icon-only button;

        aria-valuenow/min/max to ProgressBar; keep the hidden button text

  F-16  ADD A 404 SCREEN  (addresses L-10)
        Add a `path="*"` route rendering a friendly "Page not found" card

  F-17  REAL CURRENCY CONVERSION  (addresses L-11)
        Store the original amount and its currency alongside a converted

  F-18  DEPLOYMENT  (addresses L-12)

import { create } from 'zustand';
import { persist } from 'zustand/middleware';
import { v4 as uuidv4 } from 'uuid';
import type { Expense, Budget, Filters } from '../types';

interface AppState {
  expenses: Expense[];
  budgets: Budget[];
  filters: Filters;
  theme: 'light' | 'dark';
  currency: string;

  addExpense: (data: Omit<Expense, 'id' | 'createdAt'>) => void;
  updateExpense: (id: string, data: Partial<Expense>) => void;
  deleteExpense: (id: string) => void;
  setBudget: (budget: Budget) => void;
  removeBudget: (category: string, month: string) => void;
  setFilters: (filters: Partial<Filters>) => void;
  resetFilters: () => void;
  toggleTheme: () => void;
  setCurrency: (c: string) => void;
  clearAll: () => void;
}

const defaultFilters: Filters = {
  dateRange: null,
  categories: [],
  search: '',
  sortBy: 'date',
  sortOrder: 'desc',
};

export const useStore = create<AppState>()(
  persist(
    (set) => ({
      expenses: [],
      budgets: [],
      filters: defaultFilters,
      theme: 'light',
      currency: 'USD',

      addExpense: (data) =>
        set((state) => ({
          expenses: [
            {
              ...data,
              id: uuidv4(),
              createdAt: new Date().toISOString(),
            },
            ...state.expenses,
          ],
        })),

      updateExpense: (id, data) =>
        set((state) => ({
          expenses: state.expenses.map((e) =>
            e.id === id ? { ...e, ...data } : e
          ),
        })),

      deleteExpense: (id) =>
        set((state) => ({
          expenses: state.expenses.filter((e) => e.id !== id),
        })),

      setBudget: (budget) =>
        set((state) => {
          const idx = state.budgets.findIndex(
            (b) => b.category === budget.category && b.month === budget.month
          );
          const newBudget: Budget = {
            category: budget.category,
            amount: budget.amount,
            month: budget.month,
          };
          if (idx >= 0) {
            const updated = [...state.budgets];
            updated[idx] = newBudget;
            return { budgets: updated };
          }
          return { budgets: [...state.budgets, newBudget] };
        }),

      removeBudget: (category, month) =>
        set((state) => ({
          budgets: state.budgets.filter(
            (b) => !(b.category === category && b.month === month)
          ),
        })),

      setFilters: (filters) =>
        set((state) => ({
          filters: { ...state.filters, ...filters },
        })),

      resetFilters: () => set({ filters: defaultFilters }),

      toggleTheme: () =>
        set((state) => ({
          theme: state.theme === 'light' ? 'dark' : 'light',
        })),

      setCurrency: (currency) => set({ currency }),

      clearAll: () => set({ expenses: [], budgets: [] }),
    }),
    {
      name: 'expense-tracker-store',
    }
  )
);

import { parseISO, isWithinInterval } from 'date-fns';
import type { Expense, Filters } from '../types';

export function filterExpenses(expenses: Expense[], filters: Filters): Expense[] {
  let filtered = [...expenses];

  if (filters.dateRange) {
    const [start, end] = filters.dateRange;
    const startDate = parseISO(start);
    const endDate = parseISO(end);
    filtered = filtered.filter((e) => {
      const d = parseISO(e.date);
      return isWithinInterval(d, { start: startDate, end: endDate });
    });
  }

  if (filters.categories.length > 0) {
    filtered = filtered.filter((e) => filters.categories.includes(e.category));
  }

  if (filters.search) {
    const q = filters.search.toLowerCase();
    filtered = filtered.filter(
      (e) =>
        e.description.toLowerCase().includes(q) ||
        e.category.toLowerCase().includes(q)
    );
  }

  filtered.sort((a, b) => {
    let cmp = 0;
    if (filters.sortBy === 'date') cmp = a.date.localeCompare(b.date);
    else if (filters.sortBy === 'amount') cmp = a.amount - b.amount;
    else if (filters.sortBy === 'category') cmp = a.category.localeCompare(b.category);
    return filters.sortOrder === 'asc' ? cmp : -cmp;
  });

  return filtered;
}

export function getMonthKey(dateStr: string): string {
  return dateStr.slice(0, 7);
}

import type { Expense } from '../types';
import { CATEGORY_LABELS } from '../types';

export function exportToCSV(expenses: Expense[]): void {
  const headers = ['Date', 'Description', 'Category', 'Amount', 'Recurring'];
  const rows = expenses.map((e) => [
    e.date,
    `"${e.description}"`,
    CATEGORY_LABELS[e.category],
    e.amount.toFixed(2),
    e.isRecurring ? 'Yes' : 'No',
  ]);

  const csv = [headers.join(','), ...rows.map((r) => r.join(','))].join('\n');
  const blob = new Blob([csv], { type: 'text/csv' });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = `expenses-${new Date().toISOString().split('T')[0]}.csv`;
  a.click();
  URL.revokeObjectURL(url);
}

function pad(n: number): string {
  return n.toString().padStart(2, '0');
}

export function todayISO(): string {
  const d = new Date();
  return `${d.getFullYear()}-${pad(d.getMonth() + 1)}-${pad(d.getDate())}`;
}

export function currentMonthKey(): string {
  const d = new Date();
  return `${d.getFullYear()}-${pad(d.getMonth() + 1)}`;
}

export function monthKeyOf(d: Date): string {
  return `${d.getFullYear()}-${pad(d.getMonth() + 1)}`;
}

export function prevMonthKey(): string {
  const d = new Date();
  d.setDate(1);
  d.setMonth(d.getMonth() - 1);
  return monthKeyOf(d);
}

    return Object.keys(errs).length === 0;
  }

  function handleSubmit(e: React.FormEvent) {
    e.preventDefault();
    if (!validate()) return;

    const data = {
      amount: Number(form.amount),
      category: form.category,
      description: form.description.trim(),
      date: form.date,
      isRecurring: form.isRecurring,
      recurringInterval: form.isRecurring ? form.recurringInterval : undefined,
    };

    if (editExpense) {
      updateExpense(editExpense.id, data);
    } else {
      addExpense(data);
    }
    onClose();
  }

  return (
    <form onSubmit={handleSubmit} className="space-y-4">
      <div className="grid grid-cols-1 gap-4 sm:grid-cols-2">
        <Input
          label="Amount"
          type="number"
          step="0.01"
          placeholder="0.00"
          value={form.amount}
          onChange={(e) => setForm({ ...form, amount: e.target.value })}
          error={errors.amount}
        />
        <Select
          label="Category"
          options={categoryOptions}
          value={form.category}
          onChange={(e) =>
            setForm({ ...form, category: e.target.value as Category })
          }
        />
      </div>
      <Input
        label="Description"
        placeholder="What was this for?"
        value={form.description}
        onChange={(e) => setForm({ ...form, description: e.target.value })}
        error={errors.description}
      />
      <Input
        label="Date"
        type="date"
        value={form.date}
        onChange={(e) => setForm({ ...form, date: e.target.value })}
        error={errors.date}
      />
      <label className="flex items-center gap-2 text-sm text-gray-700 dark:text-gray-300">
        <input
          type="checkbox"
          checked={form.isRecurring}
          onChange={(e) =>
            setForm({ ...form, isRecurring: e.target.checked })
          }
          className="rounded border-gray-300"
        />
        Recurring expense
      </label>
      {form.isRecurring && (
        <Select
          label="Repeat every"
          options={[
            { value: 'weekly', label: 'Week' },
            { value: 'monthly', label: 'Month' },
            { value: 'yearly', label: 'Year' },
          ]}
          value={form.recurringInterval || 'monthly'}
          onChange={(e) =>
            setForm({
              ...form,
              recurringInterval: e.target.value as 'weekly' | 'monthly' | 'yearly',
            })
          }
        />
      )}
      <div className="flex justify-end gap-3 pt-2">
        <Button type="button" variant="secondary" onClick={onClose}>
          Cancel
        </Button>
        <Button type="submit">{editExpense ? 'Update' : 'Add'} Expense</Button>
      </div>
    </form>
  );
}

interface ProgressBarProps {
  value: number;
  max: number;
  label?: string;
  showPercentage?: boolean;
}

export function ProgressBar({
  value,
  max,
  label,
  showPercentage = true,
}: ProgressBarProps) {
  const pct = max > 0 ? Math.min((value / max) * 100, 100) : 0;
  const color =
    pct >= 100
      ? 'bg-red-500'
      : pct >= 80
        ? 'bg-yellow-500'
        : 'bg-green-500';

  return (
    <div className="flex flex-col gap-1">
      {(label || showPercentage) && (
        <div className="flex items-center justify-between text-sm">
          {label && (
            <span className="font-medium text-gray-700 dark:text-gray-300">
              {label}
            </span>
          )}
          {showPercentage && (
            <span className="text-gray-500 dark:text-gray-400">
              {Math.round(pct)}%
            </span>
          )}
        </div>
      )}
      <div className="h-2 w-full overflow-hidden rounded-full bg-gray-200 dark:bg-gray-700">
        <div
          className={`h-full rounded-full transition-all duration-300 ${color}`}
          style={{ width: `${pct}%` }}
        />
      </div>
    </div>
  );
}

import { AlertTriangle } from 'lucide-react';
import { useStore } from '../../store/useStore';
import { useFormatCurrency } from '../../hooks/useFormatCurrency';
import { getMonthKey } from '../../utils/filter';
import { currentMonthKey } from '../../utils/date';

export function BudgetAlertBanner() {
  const { expenses, budgets } = useStore();
  const formatCurrency = useFormatCurrency();
  const currentMonth = currentMonthKey();

  const monthExpenses = expenses.filter(
    (e) => getMonthKey(e.date) === currentMonth
  );
  const totalSpent = monthExpenses.reduce((s, e) => s + e.amount, 0);

  const overallBudget = budgets.find(
    (b) => b.category === 'overall' && b.month === currentMonth
  );

  if (!overallBudget) return null;

  const pct = (totalSpent / overallBudget.amount) * 100;

  if (pct < 80) return null;

  const isOver = pct >= 100;

  return (
    <div
      className={`flex items-start gap-3 rounded-lg border px-3 py-3 md:items-center md:px-4 ${
        isOver
          ? 'border-red-200 bg-red-50 text-red-800 dark:border-red-800 dark:bg-red-900/30 dark:text-red-300'
          : 'border-yellow-200 bg-yellow-50 text-yellow-800 dark:border-yellow-800 dark:bg-yellow-900/30 dark:text-yellow-300'
      }`}
    >
      <AlertTriangle size={18} className="mt-0.5 shrink-0 md:mt-0" />
      <p className="text-xs font-medium md:text-sm">
        {isOver
          ? `Budget exceeded! You've spent ${formatCurrency(totalSpent)} of ${formatCurrency(overallBudget.amount)}`
          : `Budget warning: You've spent ${Math.round(pct)}% (${formatCurrency(totalSpent)} of ${formatCurrency(overallBudget.amount)})`}
      </p>
    </div>
  );
}
